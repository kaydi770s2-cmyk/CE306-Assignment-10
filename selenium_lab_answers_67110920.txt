1.1 วิธีค้นหาแต่ละแบบเจอส่วนไหนของหน้าเว็บ?
1) บอกว่า by_id, by_name, by_css และ by_xpath แต่ละแบบเจอช่องกรอกชื่อ ปุ่ม หรือหัวข้อใด
2) ระบุว่าสองแบบใดเจอช่องกรอกเดียวกัน
by_id เจอ: ช่องกรอกชื่อ (Student name)
by_name เจอ: ช่องกรอกชื่อ (Student name)
by_css เจอ: ปุ่ม Register (หรือปุ่ม Load course information ขึ้นอยู่กับภาพ Screenshot ในโฟลเดอร์ reports)
by_xpath เจอ: หัวข้อ CE Course Registration (หรือ Element ตามที่กรอบส้มไฮไลต์ในภาพ)
สองแบบที่เจอช่องเดียวกันคือ: by_id และ by_name (ทั้งคู่เจอช่องกรอกชื่อ Student name)

1.2 ชื่อหน้าเว็บถูกต้อง บอกได้หรือยังว่าลงทะเบียนได้ถูกต้อง?
1) คัดลอกชื่อหน้าเว็บจากช่อง Actual
2) ตอบว่าแค่ชื่อหน้าเว็บถูกต้อง เพียงพอจะยืนยันว่าลงทะเบียนได้ถูกต้องหรือไม่ เพราะอะไร
3) บอกสิ่งที่ควรทดลองเพิ่มอีก 1 อย่าง เพื่อดูว่าลงทะเบียนได้จริงหรือไม่
ชื่อหน้าเว็บ: CE Course Registration เ
พียงพอหรือไม่ เพราะอะไร: ยังไม่เพียงพอ เพราะการตรวจสอบแค่ชื่อหน้าเว็บ (page_title) บอกได้เพียงว่าโปรแกรมเปิดเข้าถูกหน้าเว็บเท่านั้น แต่ยังไม่ได้พิสูจน์ว่าระบบทำการบันทึกข้อมูลและลงทะเบียนสำเร็จจริงหรือไม่   
สิ่งที่ควรทดลองเพิ่ม: ตรวจสอบข้อความแจ้งเตือนผลลัพธ์การลงทะเบียนบนหน้าเว็บ (เช่น ตรวจสอบว่าขึ้นข้อความลงทะเบียนสำเร็จ) หรือ ตรวจสอบการเพิ่มขึ้นของข้อมูลในฐานข้อมูล/ตารางแสดงผล

2.1 เว็บตอบกลับอย่างไรเมื่อกรอกข้อมูลทั้งสามแบบ?
1) สำหรับแต่ละกรณี ให้คัดลอก Expected (ผลที่คาด), Actual (ผลจริง) และ Status (สถานะผลทดสอบ)
2) เขียนให้ครบทั้งสามกรณีตามรูปแบบในช่องคำตอบ
valid_form: Expected = SUCCESS / Actual = SUCCESS / Status = PASS   
blank_name: Expected = NAME_REQUIRED / Actual = NAME_REQUIRED / Status = PASS   
missing_consent: Expected = CONSENT_REQUIRED / Actual = CONSENT_REQUIRED / Status = PASS

2.2 ทำไมกรณีไม่กรอกชื่อจึงได้ PASS?
1) ตามกติกา เว็บควรรับหรือปฏิเสธการลงทะเบียนเมื่อไม่กรอกชื่อ
2) เทียบ Expected กับ Actual แล้วอธิบายสั้น ๆ ว่าเหตุใด test จึงได้ PASS
เว็บควร: ปฏิเสธการลงทะเบียน และแสดงข้อความแจ้งเตือนให้กรอกชื่อ (NAME_REQUIRED)   Expected กับ Actual 
ตรงกันหรือไม่: ตรงกัน (ทั้ง Expected และ Actual เป็น NAME_REQUIRED เหมือนกัน)   
จึงได้ PASS เพราะ: การทดสอบนี้คาดหวังให้ระบบปฏิเสธ (Negative Test) เมื่อไม่กรอกชื่อแล้วเว็บปฏิเสธการลงทะเบียนและส่งข้อความตอบกลับตรงตามที่คาดหวังไว้ ผลการทดสอบจึงถูกต้องและได้สถานะเป็น PASS

3.1 ค้นหาทันทีกับรอข้อมูลก่อน ได้ผลต่างกันอย่างไร?
1) บันทึก Status ของทั้งสองกรณี และ Actual ของกรณี explicit_wait
2) คัดลอกชื่อข้อผิดพลาดที่พบใน immediate_lookup เช่นชื่อที่ลงท้ายด้วย Exception หรือ Failure
3) อธิบายว่ากรณีแรกค้นหาก่อนข้อมูลพร้อม หรือเว็บทำงานผิด โดยใช้ผลของกรณีที่รอมาช่วยอธิบาย
immediate_lookup: Status = FAIL / ชื่อข้อผิดพลาด = NoSuchElementException (หรือ TimeoutException ขึ้นอยู่กับที่แสดงใน Traceback)  
 explicit_wait: Status = PASS / Actual = COURSE_LOADED (หรือข้อความสำเร็จตามในรายงาน Lab 3) 
สาเหตุของกรณีแรกและหลักฐานที่ใช้: เกิดจากกรณีแรกพยายามค้นหา Element บนหน้าเว็บทันทีขณะที่ข้อมูลยังโหลดไม่เสร็จ (เนื่องจากหน้าเว็บมี Delay 3 วินาที) ไม่ใช่เว็บทำงานผิดพลาด หลักฐานคือเมื่อใช้ explicit_wait เพื่อรอให้ข้อมูลโหลดเสร็จก่อน ผลการทดสอบสามารถทำงานผ่านได้ (PASS) 

3.2 ถ้าหยุดรอ 3 วินาทีเท่ากันทุกครั้ง จะมีปัญหาอะไร?
1) ถ้าข้อมูลเพิ่งปรากฏหลัง 5 วินาที แต่ test หยุดรอแค่ 3 วินาทีแล้วค้นหาทันที จะพบข้อมูลหรือไม่ เพราะอะไร
2) ถ้าข้อมูลพร้อมตั้งแต่วินาทีที่ 1 แต่ test ยังหยุดรอครบ 3 วินาที จะมีเวลารอที่ไม่จำเป็นหรือไม่
3) การรอจนข้อมูลพร้อมด้วย explicit wait ช่วยในสองสถานการณ์นี้อย่างไร
ข้อมูลพร้อมหลัง 5 วินาที: ไม่พบข้อมูล เพราะ test หยุดรอแค่ 3 วินาที ซึ่งข้อมูลยังโหลดไม่เสร็จ ทำให้เกิด error เช่น NoSuchElementException หรือค้นหาองค์ประกอบไม่เจอข้อมูลพร้อมหลัง 1 วินาที: มีเวลารอที่ไม่จำเป็น เพราะ test จะต้องเสียเวลานั่งรอเปล่าๆ อีก 2 วินาทีให้ครบตามที่กำหนดไว้ ส่งผลให้การทดสอบโดยรวมช้าลงอย่างมาก
explicit wait ช่วยอย่างไร: ช่วยให้ระบบรอจนกว่าองค์ประกอบจะพร้อมใช้งานจริงตามเงื่อนไข ( Dynamic Wait ) หากข้อมูลมาเร็ว (เช่น 1 วินาที) ก็จะทำงานต่อทันทีโดยไม่ต้องรอต่อ แต่ถ้าข้อมูลมาช้าก็จะรอจนถึงเวลาสูงสุดที่กำหนดไว้ ทำให้การทดสอบมีเสถียรภาพและรวดเร็วยิ่งขึ้น

3.3 รอได้สูงสุด 10 วินาที หมายความว่าต้องรอครบทุกครั้งหรือไม่?
1) ถ้าข้อมูลพร้อมหลัง 2 วินาที test ต้องรอจนครบ 10 วินาทีหรือทำต่อได้ก่อน อธิบาย
2) ถ้าครบ 10 วินาทีแล้วยังไม่มีข้อมูล test จะทำต่อได้ตามปกติหรือเกิดข้อผิดพลาดจากการรอครบเวลา
ข้อมูลพร้อมหลัง 2 วินาที: ทำต่อได้ทันทีก่อน โดยไม่ต้องรอจนครบ 10 วินาที เพราะ Explicit Wait จะเช็กเงื่อนไขอย่างต่อเนื่อง เมื่อพบองค์ประกอบที่ต้องการแล้ว โปรแกรมจะทำงานในขั้นตอนถัดไปทันที   
ครบ 10 วินาทีแล้วยังไม่มีข้อมูล: เกิดข้อผิดพลาด โดยระบบจะหยุดทำงานและส่งข้อผิดพลาดประเภท TimeoutException เนื่องจากเกินเวลาสูงสุดที่กำหนดไว้แล้วยังไม่พบองค์ประกอบตามเงื่อนไข   

4.1 เว็บเวอร์ชันใดรับ 4 หน่วยกิต ทั้งที่กติกาให้รับได้แค่ 1-3?
1) คัดลอก Expected, Actual และ Status ของทั้งสามเวอร์ชัน
2) ระบุว่าเวอร์ชันใดทำผิดกติกา และทำผิดอย่างไร โดยอ้าง Actual ของเวอร์ชันนั้น
buggy: Expected = CREDITS_OUT_OF_RANGE / Actual = SUCCESS / Status = FAIL
fixed: Expected = CREDITS_OUT_OF_RANGE / Actual = CREDITS_OUT_OF_RANGE / Status = PASS
refactored: Expected = CREDITS_OUT_OF_RANGE / Actual = CREDITS_OUT_OF_RANGE / Status = PASS
เวอร์ชันที่ทำผิดและสิ่งที่ผิด: เวอร์ชัน buggy ทำผิดกติกา เนื่องจากเมื่อกรอกค่า 4 (ซึ่งเกินกติกา 1-3) แต่หน้าเว็บกลับส่งค่า Actual เป็น SUCCESS ซึ่งหมายถึงยอมรับการลงทะเบียนทั้งที่ไม่ควรรับ

4.2 หลังจัดโครงสร้างโค้ดใหม่ เว็บยังปฏิเสธค่า 4 ได้เหมือนเดิมหรือไม่?
1) บอกว่าผลของ fixed และ refactored เหมือนหรือต่างกันอย่างไรเมื่อรับค่า 4
2) Lab 4 ลองเฉพาะค่า 4 เรายืนยันได้หรือยังว่าเวอร์ชัน refactored รับค่า 1 และ 3 ได้ถูกต้อง เพราะอะไร
ผลของ fixed เทียบกับ refactored: เหมือนกัน โดยทั้งสองเวอร์ชันปฏิเสธการลงทะเบียนและส่งค่า Actual เป็น CREDITS_OUT_OF_RANGE ตรงกัน แสดงว่าการ Refactor โค้ดไม่ได้ทำให้การทำงานผิดเพี้ยนไปจากเดิม
ยืนยันเรื่องค่า 1 และ 3 ได้หรือยัง เพราะอะไร: ยังยืนยันไม่ได้ เพราะใน Lab 4 มีการทดสอบเฉพาะเคสที่ส่งค่า 4 เท่านั้น (Boundary/Negative Test) ยังไม่ได้ทดสอบกรณีส่งค่าที่ถูกต้องในช่วง 1 ถึง 3 (Valid Inputs) เข้าไป

5.1 ค่า 0, 1, 2, 3 และ 4 ค่าไหนเว็บรับ และค่าไหนเว็บปฏิเสธ?
1) สำหรับแต่ละค่า ให้บันทึก Actual, Status และบอกว่าเว็บรับหรือปฏิเสธข้อมูล
2) ถ้าทดลองเฉพาะค่า 2 เราจะรู้หรือไม่ว่าเว็บมีปัญหารับค่า 4 เกินกติกา เพราะอะไร
ค่า 0: Actual = CREDITS_OUT_OF_RANGE / Status = PASS / เว็บรับหรือปฏิเสธ = ปฏิเสธ   
ค่า 1: Actual = REGISTERED / Status = PASS / เว็บรับหรือปฏิเสธ = รับ   
ค่า 2: Actual = REGISTERED / Status = PASS / เว็บรับหรือปฏิเสธ = รับ   
ค่า 3: Actual = REGISTERED / Status = PASS / เว็บรับหรือปฏิเสธ = รับ   
ค่า 4: Actual = CREDITS_OUT_OF_RANGE / Status = PASS / เว็บรับหรือปฏิเสธ = ปฏิเสธ
ถ้าลองเฉพาะค่า 2 จะรู้ปัญหาของค่า 4 หรือไม่ เพราะอะไร: ไม่รู้ เพราะค่า 2 เป็นค่าปกติที่อยู่ตรงกลางช่วง (Valid Input) การทดสอบเฉพาะค่า 2 จะยืนยันได้เพียงว่าระบบทำงานปกติในกรณีทั่วไป แต่ไม่สามารถตรวจพบข้อผิดพลาดหรือบั๊กที่เกิดขึ้นเฉพาะบริเวณขอบเขต (Boundary Value) อย่างค่า 4 ได้  

5.2 คุณอยากทดลองข้อมูลแบบใดเพิ่มอีก 1 กรณี?
1) ระบุข้อมูลให้ครบ: ชื่อ วิชา หน่วยกิต และติ๊กยืนยันหรือไม่
2) บอกว่าเว็บควรรับหรือปฏิเสธ พร้อมระบุข้อความตอบกลับที่คาดไว้
3) อธิบายเหตุผลโดยใช้กติกาของเว็บ กรณีที่เสนอควรต่างจากกรณีเดิมใน Lab 2 และ Lab 5
ชื่อที่จะกรอก: CE Student   
วิชา: Selenium Python   
หน่วยกิต: -1   
ติ๊กยืนยันหรือไม่: ติ๊กยืนยัน   
เว็บควรรับหรือปฏิเสธ / ข้อความที่คาด: ปฏิเสธ / ข้อความตอบกลับที่คาดไว้คือ CREDITS_OUT_OF_RANGE   
เหตุผลและสิ่งที่ต่างจากกรณีเดิม: เพราะกติกาของเว็บกำหนดให้หน่วยกิตต้องเป็นจำนวนเต็มตั้งแต่ 1 ถึง 3 เท่านั้น ค่า -1 เป็นค่าติดลบซึ่งอยู่นอกช่วงกติกา (Boundary/Invalid Input) ซึ่งต่างจาก Lab 2 ที่ทดสอบเรื่องการลืมกรอกข้อมูล/การติ๊กยืนยัน และต่างจาก Lab 5 ที่ทดสอบเฉพาะค่า 0 ถึง 4 การทดสอบค่าติดลบจะช่วยยืนยันว่าระบบปฏิเสธข้อมูลตัวเลขที่ไม่อยู่ในเงื่อนไขได้อย่างครอบคลุม   

6.1 สองกรณีนี้ไม่ผ่านด้วยสาเหตุเดียวกันหรือไม่?
1) สำหรับ immediate_lookup บอกว่าปัญหาเกิดจากวิธีรอของ test หรือการตรวจหน่วยกิตของเว็บ พร้อมยกหลักฐาน 1 อย่าง
2) สำหรับ credits_4_buggy บอกว่าปัญหาเกิดจากวิธีรอของ test หรือการตรวจหน่วยกิตของเว็บ พร้อมยกหลักฐาน 1 อย่าง
3) สรุปสั้น ๆ ว่าทั้งสองกรณีมีสาเหตุเหมือนหรือต่างกันอย่างไร
immediate_lookup: สาเหตุ = เกิดจากวิธีรอของ test / หลักฐาน = เกิด NoSuchElementException ใน Traceback เนื่องจากไม่ได้รอให้องค์ประกอบบนหน้าเว็บโหลดเสร็จก่อน   
credits_4_buggy: สาเหตุ = เกิดจากการตรวจหน่วยกิตของเว็บ / หลักฐาน = ค่า Expected เป็น CREDITS_OUT_OF_RANGE แต่ Actual เป็น SUCCESS แสดงว่าเว็บยอมรับค่า 4 ซึ่งผิดกติกา   
สาเหตุเหมือนหรือต่างกันอย่างไร: ต่างกันอย่างสิ้นเชิง โดยกรณีแรก (immediate_lookup) ปัญหาเกิดจากฝั่งสคริปต์ทดสอบ (Test Script) ที่ไม่มีวิธีรอข้อมูลที่ดี แต่กรณีหลัง (credits_4_buggy) ปัญหาเกิดจากระบบเว็บที่ทดสอบ (Application Under Test) มีบั๊กในตรรกะการตรวจสอบข้อมูล (Business Logic)
